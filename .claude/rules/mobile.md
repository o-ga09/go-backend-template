# クライアントルール（React Native / Expo）

対象: リポジトリルートの `App.tsx` / `src/`。
**このプロジェクトのクライアントは RN/Expo アプリ1つだけ。Web フロントエンド（Next.js）は存在しない。**
バックエンド（Go / Echo / GORM）は `architecture.md` ほかを参照。

## 技術スタック

React Native 0.86 + Expo 57 + React 19 + TypeScript + **TanStack Query**。パッケージマネージャは **pnpm**。

| 用途 | コマンド |
|---|---|
| 起動 | `pnpm start` / `pnpm ios` / `pnpm android` / `pnpm web` |
| 型チェック | `pnpm typecheck` |
| Lint | `pnpm lint` / `pnpm lint:fix`（**oxlint**。ESLint ではない） |
| テスト（ロジック） | `pnpm test` / `pnpm test:watch`（**Vitest**） |
| テスト（VRT） | `pnpm test:vrt` / `pnpm test:vrt:watch`（**jest-expo** + `@testing-library/react-native`） |

## デザインの正本（Pencil）🔴

- 画面デザインの正本は `docs/design/design.pen`（Pencil）。**実装対象の画面がまだ `design.pen` に無い場合は、コードを書く前に Pencil でデザインを起こすところから着手する。** デザインなしで画面を実装しない
- **デザインと実装が食い違ったら、Pencil デザインを優先する。** コード側の見た目をデザインに合わせて直す。「実装が先にあるからデザイン側を実装に合わせる」は禁止
- `.pen` ファイルへのアクセスは `pencil` MCP ツール経由のみ（`Read`/`Grep` では読めない）
- デザイントークンの正は `DESIGN.md`（`design.pen` の `variables` のスナップショット）。値を変えるときは Pencil（`get_variables`/`set_variables`）→ `DESIGN.md` の順で反映する

## ディレクトリ構成

**React Native 標準のフラット構成に寄せる。** feature ごとの Clean Architecture（domain/data/presentation）は採用しない。

```
App.tsx
src/
├── interview/       インタビュー進行ロジック（純粋関数。既存）
├── screens/         画面コンポーネント
├── components/      共通コンポーネント
├── hooks/           カスタムフック
├── lib/
│   ├── api/         API クライアント + TanStack Query フック
│   └── validations/ Zod スキーマ（ドメインごとにファイル分割）
├── providers/       QueryProvider など
├── storage/         ローカル保存（SQLite）
└── theme/           デザイントークン（DESIGN.md の写し）
```

## 最重要：ロジックを画面に書かない 🔴

このプロダクトの価値は原則10箇条にあり、**原則はテストでしか守られない。**
`package.json` の vitest 対象は `src/**/*.{test,spec}.ts` で、**RN コンポーネントは対象外**。

つまり **画面に書いたロジックは vitest では一切テストされない。**
画面側には別途 jest-expo による VRT（`*.test.tsx` / `jest.config.js`）があるが、これは**見た目のスナップショット比較**であり、
分岐条件・掘り下げ判定・進行終了判定のようなロジックの正しさは検証しない。**ロジックの正しさは引き続き純粋関数 + vitest でのみ担保する。**

```ts
// 誤: 画面の中で判定する（テストされない＝原則が守られない）
function InterviewScreen() {
  if (answer.includes('特にない')) { setDigDeeper(true) }
}

// 正: 純粋関数に出して vitest でテストし、画面は結果を使うだけ
// src/interview/interview.ts
export function shouldDigDeeper(answer: string, alreadyDug: boolean): boolean { ... }
```

**画面に置いてよいのは表示と入力の受け渡しだけ。** 以下は必ず純粋関数に置く:

- 質問の進行・終了判定（原則7 / FR-03-03）
- 「特にない」検知と掘り下げの発火（原則4 / FR-04）
- 素材量の判定（原則6 / FR-03-12）
- 無料／有料の権利判定

## データフェッチ

- サーバー状態は **TanStack Query** で管理する。`useState` + `useEffect` で自前にフェッチしない
- クエリ／ミューテーションフックは `src/lib/api/` にドメインごとに定義し、画面からはフックだけを使う
- 画面から `fetch` / HTTP クライアントを直接呼ばない
- `QueryClientProvider` は `src/providers/` に置き、`App.tsx` でラップする

```tsx
// 正: TanStack Query フック経由
const { data, isLoading } = useDraft(sessionId)
const { mutateAsync: postAnswer } = usePostAnswer()

// 誤: 画面から直接フェッチ
const res = await fetch(`${BASE_URL}/sessions/${id}/draft`)
```

### このプロダクト固有の注意

- **回答の送信ミューテーションは、ローカル確定保存の後に行う**（NFR-02-03：通信断でも入力を失わない）
- **下書き生成は失敗しても回答を失わず再試行できること**（FR-06-11）。生成は課金コストが発生するため自動リトライ回数を絞る
- 生成は最大30秒かかる（NFR-01-04）。`isPending` を進行表示に必ず繋ぐ（FR-06-10）
- **APIキー・プロンプトテンプレートをクライアントに含めない**（`ADR-0006`）。LLM 呼び出しは必ずバックエンド経由

## バリデーション

- 入力バリデーションは **Zod** スキーマで定義する
- フォームを使う画面では **React Hook Form** + `@hookform/resolvers/zod` を使う
- スキーマは `src/lib/validations/` にドメインごとのファイルで定義する
- API レスポンスの型も Zod スキーマから導出し、`any` を使わない

**ただしインタビューの回答入力にバリデーションで詰まらせない。** 「まとまってなくていい」が前提であり（`docs/interview-design.md`）、
必須チェック・文字数下限でユーザーを止めない。空でも「わからない」で先に進める（FR-03-05）。

## 状態管理

- **サーバー状態は TanStack Query、UI状態は `useState` / `useReducer`** と役割を分ける
- 状態管理ライブラリ（Redux 等）は導入しない
- **セッションの進行状態は `src/interview/` の純粋関数が返す値を持つだけにする。**画面が状態遷移を判断しない
- グローバルに持つのは「権利（有料/無料）」「選択中の推し」程度。Context で足りる

## コンポーネント設計

- 1ファイル = 1コンポーネント。画面は `src/screens/`、再利用部品は `src/components/`
- `StyleSheet.create` を使う。インラインスタイルを乱用しない
- **色・余白・フォントサイズをハードコードしない。** `src/theme/` のトークン経由で参照する（NFR-05-01）

```tsx
// 誤: 値の直書き
<Text style={{ fontSize: 14.5, color: '#3A4800' }}>

// 正: トークン参照
<Text style={styles.body}>
const styles = StyleSheet.create({
  body: { fontSize: theme.text.bodyLg, color: theme.color.primaryText },
})
```

トークンの正は `DESIGN.md`。値を変えるときは `DESIGN.md` を先に更新する。

## 型

- `any` を使わない
- 質問キーは `'q1' | 'q2' | ...` のユニオン型にする。文字列リテラルを散らさない

## ローカル保存

`ADR-0007`：端末ローカル＋暗号化同期。**ローカルは平文キャッシュ**として持つ（端末内は OS の保護に委ねる）。

- ローカル DB は **SQLite**（Expo の SQLite モジュール）。用途はオフライン閲覧と無料範囲の「最新1件保存」
- サーバー同期は暗号化して送る。**クライアントで暗号化しない**（鍵はサーバー側の Cloud KMS 管理）
- 同期の競合解決は **last-write-wins**。単一ユーザー・実質単一デバイス利用を前提にする（`ADR-0007`）

```
[端末 SQLite（平文キャッシュ）] ──HTTPS──> [Cloud Run] ──暗号化して保存──> [TiDB]
```

## 最重要：データを失わない 🔴

`NFR-02-01`「ユーザー操作を伴わないデータ消失の発生率を0とする」は**モバイルで最も破られやすい要件**。
iOS はメモリ逼迫時に OS 判断でアプリを終了させるため、メモリ上にしかない入力は**ランダムに消える**（`ADR-0003`）。

| 場面 | 必須の挙動 | 要件 |
|---|---|---|
| 設問への回答が確定 | **その時点でローカルへ永続化。**セッション完了を待たない | NFR-02-02 |
| アプリがバックグラウンドへ | 編集中の下書きを保存 | NFR-02-01 |
| OS がアプリを終了 | 再起動時に中断地点から再開できる | FR-03-08 |
| 通信断・生成失敗 | 回答を保持したまま復帰・再試行できる | NFR-02-03 / FR-06-11 |

- `AppState` の `background` / `inactive` 遷移で保存をフラッシュする
- **保存は「送信の成功」を待たない。**ローカル確定 → 送信 の順
- **タイマー・回数・アプリ終了を契機にデータを消す実装を書かない**（原則10 / FR-08-90）

## オフライン

| 要件 | 挙動 |
|---|---|
| NFR-07-01 | 保存済みの下書き・過去セッションは**オフラインで閲覧できる**（必須） |
| NFR-07-02 | インタビューの回答入力はオフラインでも継続でき、復帰後に同期（推奨） |
| NFR-07-03 | 下書き生成には通信が必要。**失敗時にその旨を明示する**（必須） |

生成が通信必須であることを、失敗して初めて知らせるのではなく、状態として扱う。

## 課金（RevenueCat）

- 課金基盤は **RevenueCat**（Shipaton 2026 の応募要件）
- ユーザー識別は **RevenueCat の匿名 App User ID**。MVP では独自の認証を持たない（`ADR-0006`）
- **権利（Entitlement）は1つにまとめる。** 月額・年額・買い切りのどれからでも同じ権利が付く（FR-11-03 / `ADR-0005`）
- 購入の復元導線を必ず用意する（FR-11-04）
- **サブスク保有中に買い切りを購入しようとしたら、自動更新の停止を案内する**（FR-11-05）。二重課金は最悪のレビューを生む
- 価格・プラン構成はアプリ再提出なしに変更できるようにする（FR-11-06。Week 6 で価格を変える前提）

権利の判定ロジックは**純粋関数に切り出して vitest でテストする**（上記「ロジックを画面に書かない」）。

## OS 機能・権限

- **不要な権限を要求しない。** MVP で必要なのは通信のみ。カメラ・連絡先・位置情報・通知の権限を求めない
- 書き出しは OS 標準の共有シート／クリップボードを使う（FR-08-01）
- **スクリーンショットの禁止・検知を実装しない**（原則10 / FR-08-91）。iOS に阻止する公式APIはなく、かつスクショは最大の無料集客経路

## 分析・トラッキング

- 行動分析イベントに**本文・回答・推しの名前を載せない**（FR-13-91 / FR-13-92）
- トラッキング同意（ATT 等）に対応し、**非同意でも全機能を制限なく提供する**（NFR-12-06 / FR-13-10）
- 分析のオプトアウト導線を設定画面に置く

## パフォーマンス

`NFR-01` の目標値を UI 側で守る。

| 指標 | 目標 |
|---|---|
| 質問から次の質問への遷移 | 0.3秒以内。**ネットワーク往復を待たせない**（検知語の判定は端末側で行う） |
| 部分一致の掘り下げ提示 | 0.5秒以内 |
| アプリ起動から操作可能まで | 2秒以内 |
| 保存済みセッション一覧 | 1秒以内 |

- 一覧は `FlatList` を使い、全件を一度に描画しない
- 手紙本文の長文表示で再レンダリングを起こさない（入力中の state を親に持ち上げない）

## アクセシビリティ

- 文字サイズの OS 設定に追随し、レイアウトが破綻しないこと（NFR-05-04）
- タップ対象は十分な大きさを確保する（NFR-05-03。片手・移動中の利用を想定）
- スクリーンリーダーで主要導線を操作できること（NFR-05-05）

## プラットフォーム差異

- **iOS を主対象**、Android は同時提供可能な範囲（NFR-11-03）
- `Platform.OS` による分岐は最小限にし、分岐が増えたらコンポーネントを分ける
- `pnpm web`（Expo Web）は開発時の確認用。**Web を提供対象としない**

## 禁止事項 🚫

- **質問文・掘り下げ文言をコンポーネント内に直書きしない。** `src/interview/` の定数に集約し、`docs/interview-design.md` と1:1で対応させる（FR-03-04）
- 画面に原則由来のロジックを書かない
- デザイントークンの値をハードコードしない
- 画面から直接フェッチしない（TanStack Query フック経由）
- ユーザー操作を伴わないデータ削除（原則10 / FR-08-90）
- スクリーンショットの禁止・警告・検知（FR-08-91）
- 書き出し機能の有料化（FR-08-92）
- 本文・回答・推しの名前を分析イベントに載せる（FR-13-91 / FR-13-92）
- 送信を促す通知・文言（原則8）
- 喪失の恐怖を動機にした課金訴求（原則10 / FR-10-91）

## 禁止表現の検出（NFR-08-04）

対象は NFR-08-01（送信を促す表現）・NFR-08-02（否定的な評価・採点）・FR-10-91（喪失の恐怖を動機にした訴求）・FR-14-92（評価内容を誘導する文言）の4項目（詳細は Issue #43）。

- **直接的な言い回し**（「送りましょう」「消えてしまいます」「星5をお願いします」等）は `src/lib/copy-guard/bannedPhrases.test.ts` が `src/**/*.{ts,tsx}` を機械的にスキャンして検出する（`pnpm test` に乗る。新規CIジョブは作らない）
- **婉曲・言い換え表現**（例:「そろそろ手紙にしても良い頃かも」のような文脈依存の訴求、NFR-08-02のうち「もう少し具体的だと」のような婉曲な指摘）は正規表現では誤検知・見逃しの両方が起きるため自動検出の対象外。**レビュー時に上記4項目を観点としてチェックする**
- 新しい画面・文言を追加するときは、直接的な言い回しは上記テストが落ちることで気づける。婉曲表現はレビュアーが目視で確認する
