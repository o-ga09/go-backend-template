# 機能設計スキル

新機能・新ドメインについて、要件を整理してからこのリポジトリのアーキテクチャ方針に沿った設計判断を行うワークフロー。**このスキル自体はコードを書かない。** 設計が固まったら実装スキルに引き継ぐ。

---

## Step 1: 要件を整理する

ユーザーの依頼が曖昧な場合、実装に入る前に以下を明確にする（グローバルルール「調査タスク・未Issueタスクの実装を始めない」に対応）。

- 解決したい課題・ユーザーストーリーは何か
- スコープの境界（今回やること／やらないこと）
- 受け入れ条件（何ができれば完了か）
- 対応する GitHub Issue はあるか（無ければ、先に Issue を作るかどうかユーザーに確認する）

不明点は `AskUserQuestion` 等で確認し、憶測で設計を進めない。

---

## Step 2: ドメインを特定する

- 既存ドメイン（`internal/domain/<name>/`）の拡張か、新規ドメインの追加かを判断する
- 新規ドメインの場合、1ドメイン1パッケージ（`package-structure.md`）に沿って `internal/domain/<name>/` を新設する想定で設計する
- 他ドメインの状態を参照する必要がある場合（例: 注文ドメインが在庫ドメインの在庫数を必要とする）は、**ドメイン間に新しい依存を作らない**設計にする。呼び出し側（ハンドラ／service層）が相手ドメインを呼び、判定結果だけを対象ドメインの純粋関数に渡す設計にする（`architecture.md`）

---

## Step 3: レイヤー構成を決める

`architecture.md` の基本方針（server → domain の2層がデフォルト）に従い、usecase層（`internal/service/`）が必要かどうかを判定する。

| 判定基準 | 結果 |
|---|---|
| 単一リポジトリへの読み書きのみ | 2層（ハンドラが domain を直接呼ぶ）。`internal/service/` は作らない |
| 複数リポジトリをまたぐオーケストレーションが必要 | usecase層を挟む |
| 外部API呼び出し（決済・通知など）を伴う | usecase層を挟む |
| 暗号化/復号（KMS呼び出し）を伴う | usecase層を挟む |

**usecase層を作る場合も、ドメインルール自体（バリデーション・状態遷移の可否判定）は domain 層の純粋関数に置く。** usecase はそれを呼び出すだけにする。

---

## Step 4: データモデルを設計する

- 新規テーブルが必要な場合、`pkg/model.BaseModel`（`ID`/`Version`/`CreatedAt`/`UpdatedAt`）を埋め込む前提で設計する
- 暗号化やカラム名の詰め替えが必要なドメインかどうかを判定する（該当する場合のみ domain＝DBモデルの前提から外れ、変換用構造体を用意する）
- 監査項目（作成者など）が必要か確認し、必要なら `BaseModel` への追加を検討する
- 楽観ロック・採番・タイムスタンプは GORM プラグイン任せにする設計にする（アプリケーションコードで手書きしない）

テーブル定義そのものの作成（マイグレーションSQL）は `migration-db-schema` スキルに引き継ぐ。

---

## Step 5: トランザクション境界とエラーハンドリング方針を決める

- 複数テーブルへの書き込みがあるか → `ITransactionManager.RunInTx` でラップする境界を明確にする
- 外部API呼び出し・暗号化処理がある場合、**トランザクションの外**に置く設計にする（`transaction.md`）
- 新しいドメインエラー（在庫不足・上限超過など）が必要か洗い出し、`pkg/errors/errors.go` に追加する sentinel エラー（`ergo.NewSentinel`）の候補を挙げる
- エラーメッセージに機密情報を含めない設計になっているか確認する（`error-handling.md`）

---

## Step 6: API / 画面インターフェースを整理する

- Backend: 追加するエンドポイント（メソッド・パス・リクエスト/レスポンス）を列挙する
- Frontend: 追加する画面・コンポーネント、TanStack Query のクエリ/ミューテーション、Zod スキーマの概要を列挙する
- フロントエンド・バックエンドの型の対応関係（レスポンス型とAPIクライアントの型）を確認する

---

## Step 7: 設計内容をまとめる

以下の形式で設計内容を出力し、ユーザーと合意する。

```markdown
## 機能設計: <機能名>

### 要件
- 解決したい課題:
- スコープ:
- 受け入れ条件:

### ドメイン
- 対象ドメイン: <既存 / 新規:internal/domain/xxx>
- 他ドメインとの関係:

### レイヤー構成
- usecase層: <要 / 不要>（理由: ...）

### データモデル
- 新規/変更テーブル:
- BaseModelからの逸脱: <あり（理由） / なし>

### トランザクション・エラー
- トランザクション境界:
- 外部API呼び出し:
- 新規sentinelエラー:

### インターフェース
- Backend エンドポイント:
- Frontend 画面/コンポーネント:

### 実装への引き継ぎ
- [ ] `migration-db-schema` でスキーマ追加
- [ ] `implement-api` でエンドポイント実装
- [ ] `implement-component` で画面実装
```

規模の大きい設計判断（他ドメインへの影響が大きい・既存方針からの逸脱を含む等）は `DESIGN.md` に設計判断として追記する。ユーザーに追記の要否を確認する。

---

## 実装フェーズへの引き継ぎ

設計がユーザーと合意できたら、このスキルでの作業は完了。実装は以下のスキルに引き継ぐ（このスキル自身はファイルを編集しない）。

- Backend: `implement-api`
- Frontend: `implement-component`
- DBスキーマ: `migration-db-schema`
